# Linux Direct 403 指纹验证

## 结论先行

Ubuntu 上的 Direct 403 来自 native transport 的 `auto` TLS/HTTP2 指纹，不是 Service Token、Codex OAuth 或代理配置。改用显式现代 Chrome profile 后，四组测试全部成功。

## 背景

衡迹 Android 客户端通过 Tailscale 调用 hx470 上的 CodexTask 服务。服务鉴权和任务提交成功，但 Direct 返回：

```text
DIRECT_AUTH_FAILED: Direct authentication failed with HTTP 403
```

响应体实际是 HTML 拦截页，不是 Codex API JSON。

## 对比目标 / 实验问题

验证 403 是否由 OAuth、代理或 native TLS/HTTP2 指纹造成。

## 范围与配置

| 项目 | 内容 | 说明 |
|---|---|---|
| 服务端 | hx470，Linux x64 | CodexTask 0.2.9 |
| 模型 | `gpt-5.6-sol` | Direct 文本最小请求 |
| 代理 | `socks5h://127.0.0.1:7890` | Clash Verge |
| 对照 | 官方 Codex CLI | 同一 OAuth、同一服务器、同一网络 |

## 结果总览

| 场景 | JA3 | Akamai HTTP/2 | 结果 |
|---|---|---|---|
| native auto | `auto` | `auto` | HTML 403 |
| 显式 profile | `chrome124` | `chrome119` | `OK` |
| 显式 profile | `chrome131` | `chrome119` | `OK` |
| 显式 profile | `chrome133` | `chrome119` | `OK` |
| 显式 profile | `chrome150` | `chrome119` | `OK` |
| 官方 Codex CLI | 官方实现 | 官方实现 | `OK` |

## 结论

`@ossiana/node-libcurl` 的 `auto` profile 在该 Linux 环境被 ChatGPT 前端拦截。CodexTask 应为每个安装持久化一个明确的受支持 profile，并在创建 native session 时显式传入。HTML 403 应报告为上游前端拦截，不能继续误导为 OAuth 失效。

## 边界与未覆盖问题

- 本次矩阵验证的是 Direct 文本请求；图片请求复用同一 transport，但仍需部署后做一次真实图片 smoke test。
- Direct 使用私有接口，即使指纹固定，服务端协议和风控仍可能变化。
